## A. 한 문장 주제

저계측 제조환경에서 집계 전력 이력만으로 15~60분 수요를 예측하고, 각 예측의 **신뢰도**와
**적응형 피크 위험**을 함께 산출해, 비용 인식 h60→h15 에스컬레이션으로 경보를 올리며,
불확실성의 원인을 현재 변수로 지목할 수 없는 구간을 **정보부족**으로 분류해 작업자에게 넘기는 시스템.

## B. 해결하려는 실제 문제

- 설비 단위 계측이 없는 공장은 "언제 최대수요가 올라오는가"를 집계 전력만으로 판단해야 한다.
- 단일 평균오차 지표는 **언제 믿어도 되는지**를 알려주지 않는다. 피크 구간·전환 구간에서 오차가 몰린다.
- [사실] 원본구간 h60 MAE 8.76 kw 이지만 신뢰도 LOW 밴드 MAE 13.85, HIGH 밴드 4.70 kw
  (`23_baseline_reliability_metrics.csv`). 평균값 하나로 운영 판단을 내릴 수 없다.
- 시스템 책임은 **예측 → 신뢰도 → 경보 → 진단정보 → 작업자 전달**에서 끝난다. 설비 제어는 범위 밖이다.

## C. 입력 데이터

- KAMP 「자원 최적화 AI 데이터셋」 `okm_augumented_2021.csv` (2021년, 1시간 4분할 = 15분 수요).
- 공통 행집합 23,548행(워밍업·결측 제거), OOF 평가 19,620행, 원본구간(7/1~9/14) 7,288행 **[사실]**.
- CORE 입력: 집계 전력 이력 14종 / 달력·계절요금 8종 / 동시각 기상관측 4종 / 생산 4종.
- PUBLIC 추가 입력: 공휴일·근무일 달력 6종(holidays 0.83), NOAA ISD 외부기상 12종, 태양기하·요금시간대 5종.
- 영구 제외: `평균`(= 15/30/45/60분 타깃의 산술평균 → 직접 누수), `공장인원`(생산량과 spearman 0.994), `인건비`(상수).
  근거·가용성 전표: `23_baseline_feature_metadata.csv` (56행).

## D. 전체 시스템 구조

```
저계측 입력 → 다중시점 예측(h15~h60) → CQR 구간·신뢰도 밴드 → 적응형 피크위험(직전30일 p95)
            → 비용인식 경보(h60 조기 → h15 확인) → 2축 정보부족 진단 → 작업자 등급·사유 전달
```
그림: `23_baseline_fig1_architecture.png` ~ `fig6_operator_routing.png` (6장)
단일 명령 재현: `python3 analysis/final_baseline/run_baseline.py --config analysis/final_baseline/config.yaml`

## E. 각 모듈의 역할

| 모듈 | 파일 | 역할 | 핵심 규칙 |
|---|---|---|---|
| A 특성 | `features.py` | CORE/PUBLIC 단일 특성 빌더 + 메타데이터 | 결정시점 정보만, 외부 캐시 없으면 CORE 강등 |
| B 예측 | `models.py`, `pipeline.py` | h15/30/45/60 direct HGB + 기준선 4종 | 딥러닝 미사용(근거 보고서 10·15) |
| C 신뢰도 | `models.py` | 분위 HGB + **조건부 conformal(현재수요 TRAIN 3분위 그룹)** + 밴드 + Mahalanobis OOD | 분위모델 TRAIN, 그룹별 보정분위 CAL, 밴드컷 CAL, OOD컷 TRAIN p99 |
| D 레짐 | `pipeline.py` | LOW_LOAD / STABLE_OPERATION / TRANSITION_LIKE | 규칙형 채택, ramp 컷은 TRAIN p90 |
| E 피크 | `features.py` | 직전 30일 p95 적응형 임계 + margin + 위험점수 | `kw.shift(1).rolling(2880)` — 과거만 |
| F 정책 | `policy.py` | h60→h15 에스컬레이션 스윕, 게이트 3종, 비용비 7종 | 분위→임계값 변환을 폴드별 CAL 예측분포에서 수행 |
| G 파레토 | `policy.py` | 비용 × 선행시간 2목적 비지배 집합 | 가중합으로 접지 않음 |
| H 진단 | `diagnosis.py` | 신뢰도 × 설명가능성 2×2 라우팅, 정보부족 플래그 | 설비 지목 금지, '정보 유형'까지만 |
| J 작업자 | `diagnosis.py` | 등급 6종 + 사실기반 사유 + 필요 정보유형 | 물리적 조치 문구 0건(자동 검증) |
| 배포 | `run_baseline.py`, `inference.py` | 전체 과거로 재적합 → joblib 산출물 + 추론 함수 | 배포 적합 in-sample 성능은 평가로 보고하지 않음 |

> **정정 (2026-10-06, 보고서 30)**: 상태 개수 `3` 은 **설계 선택**이다. 군집 개수 자체를 점검하면
> silhouette 최적은 k=4 이고 규칙 라벨과 KMeans3 의 ARI 는 0.21 이다. 또한 **상태별 개별 예측모델은
> 4개 horizon 전부에서 전체 모델보다 나빠(h60 +0.756 kw) 채택하지 않았다.** 상태의 역할은 진단·라우팅이다.

### 레짐 탐지기 선택 근거
결정시점 안전성·재현성·계산량에서 규칙형이 가장 단순하고, 보고서 20에서 4개 정의가 모두 3구조를
재현했으므로(평균 ARI 0.441) 가장 가벼운 정의를 채택했다. 진단용 비교로 TRAIN 적합 GMM3 와의
일치도를 매 폴드 기록한다 — **[사실]** ARI 0.242 / 0.335 / 0.489 / 0.464 / 0.436
(`23_baseline_regime_agreement.csv`). **[해석]** 두 정의는 겹치지만 동일하지 않다. GMM3 의 전환형
점유율이 29~34% 로 규칙형 13~18% 보다 넓다.

- **[사실]** 그럼에도 누수 없는 선택 규칙(폴드별 CAL MAE 1% 이상 개선 + 피크조건 MAE 2% 초과 악화 금지
  + 구간폭 5% 초과 확대 금지)은 20개 fold×horizon 중 **0개**에서 PUBLIC 을 채택했다.
  CAL 상대개선이 1% 이상인 칸은 2개뿐이고(fold4 h45 +1.59%, fold4 h60 +6.29%), 둘 다 피크조건 MAE
  악화(+6.8%, +9.9%)로 규칙에서 탈락했다.
- **[해석]** 보고서 18이 보고한 h60 이득은 **사후적으로만 관측된다**. 시점 t 에서 사용 가능한 정보
  (과거 CAL 구간 성능)로는 그 이득을 식별할 수 없었다. 즉 "외부 공공데이터를 쓰면 h60 이 좋아진다"는
  결론은 유효하지만, **누수 없이 그 선택을 내릴 근거는 현재 데이터에서 확보되지 않았다.**
  이것은 보고서 18에 대한 정정이 아니라 **적용 조건의 제한**이다.
- **[사실]** 선택 모드(CORE)에서 LOW+OOD 비중은 h15~h60 0.238~0.270, 피크구간 coverage 0.227~0.358,
  전환형 MAE 8.11~10.81 로 남아 있다. 공공데이터는 이 지표들을 해소하지 못했다(보고서 18 CASE 2 유지).
- **[가설]** CAL 구간이 증강(1~6월) 영역을 많이 포함해 외부 기상·태양기하 특성의 일반화를 과소평가할 수 있다.
  원본구간만으로 CAL 을 구성할 만큼의 데이터가 없어 검증하지 못했다.

## I. 다중시점 경보 성능

> **정정 (2026-10-05, 보고서 28)**: 이 절의 수치는 ① 조기·확인 단계의 **목표시각이 어긋난 구현**과
> ② **평가창에서 정책을 선택한 사후 최적화**의 결과다. 목표시각을 맞추고 정책선택(SEL)·평가(TEST)를
> 분리하면 순차 경보는 TEST 0/7 비용비에서 단일 경보를 이기지 못한다 → **"7/7 우월" 주장 철회**.

## J. 비용 × 선행시간 Pareto

> **정정**: 아래 파레토도 평가창 기반 후보 탐색이다. 선택-평가를 분리한 뒤에도 **선행시간을 제약할 때만**
> 순차 구조가 선택된다(보고서 28 §2: 선행 ≥30분 제약 → h60 q0.78 → h45 q0.90, 선행 45분·포착 0.529).
